# 架构总览与决策指南（体系总线）

其余架构页是**节点**，本页是**总线**。单独读任何一篇都像读小说的一章——知道讲了什么，却不知道它在整本书的哪一页、前后该接什么。这一页用「六步决策旅程」把 25 篇架构页串成一个系统：先建立主干，再按需下钻。

> 核心认知：架构不是选一个"最佳模式"，而是**分层做一组相互咬合的决策**。六步由外到内、由地基到叠加，前一步未定，后一步无从谈起。

## 六步走：从地基到叠加

### 第 1 步 · 边界形态（单体还是微服务？）
决定"怎么部署、模块边界画在哪"。**默认模块化单体**——单进程、内部强边界，运维简单又能清晰解耦；只有当部署/团队强制（多团队独立部署、伸缩曲线差异巨大）才拆微服务。二者是"同一模块代码的二态"，模块划分方式一致。
- 页：[模块化单体](modular-monolith.md) · [微服务](microservices.md)

### 第 2 步 · 模块内部结构（代码怎么组织）
决定"依赖朝哪、按技术分层还是按功能"。想要依赖向内、易换存储 → [整洁架构](clean-architecture.md)；想让业务完全不依赖基础设施、I/O 走端口 → [六边形架构](hexagonal-architecture.md)；功能多、改动常跨整条用例 → [垂直切片](vertical-slice.md)；用 [解决方案分层与项目引用](solution-structure.md) 把边界钉成编译期依赖。三者目标一致，可混用。

### 第 3 步 · 领域建模（DDD 战术构件）
当领域有真实逻辑时，用富领域模型而非贫血 CRUD。概念有身份与生命周期 → [实体与聚合根](entities.md)；无标识描述 → [值对象](value-objects.md)；聚合内"已发生的事" → [领域事件](domain-events.md)；跨聚合业务 → [领域/应用服务](domain-application-services.md)；跨层传输 → [DTO](dto.md)；可组合查询条件 → [规约模式](specification-pattern.md)。总览见 [DDD](ddd.md)。

### 第 4 步 · 跨边界契约（战略设计与边界）
当系统不止一个边界：模型互相污染/跨库耦合 → 划 [限界上下文](bounded-context.md)（用通用语言 + 防腐层）；对外暴露能力 → 定 [API 设计](api-design.md) 契约；任何重大取舍 → 写 [ADR](adr.md) 留痕。

### 第 5 步 · 按需叠加的能力（横切，出现痛点才开）
- 读写负载不对称、读要独立优化 → [CQRS](cqrs.md)（先轻量同库）。
- 需完整审计轨迹/时间旅行 → [事件溯源](event-sourcing.md)（常配 CQRS）。
- 跨服务最终一致、怕 2PC → [事件驱动](event-driven.md)（集成事件 + 发件箱）+ [Saga](saga.md)（补偿）。
- 多租户数据隔离 → [多租户](multi-tenancy.md)；统一审计/软删除 → [审计与软删除](auditing-soft-delete.md)。
- 怕边界腐化 → [架构测试](architecture-tests.md) 把规则锁进 CI。

### 第 6 步 · 边缘（怎么暴露给客户端）
多类客户端需不同聚合视图、怕上帝网关 → [API 网关与 BFF](api-gateway-bff.md)（仅用官方 YARP），在边缘做路由/聚合/统一认证限流。

**导览配套**：[企业级架构模式（导览）](enterprise-patterns.md) · [组合与架构模式](../patterns/composition.md) · [设计与可维护性反模式](../anti-patterns/design-antipatterns.md)

## 决策速查：面对 X，用 Y

| 你面对的情况 | 优先采用 |
|------|------|
| 单团队、部署简单、领域在演化 | [模块化单体](modular-monolith.md) |
| 多团队独立部署 / 伸缩曲线差异大 | [微服务](microservices.md) |
| 想依赖向内、易换存储、易测 | [整洁架构](clean-architecture.md) 或 [六边形架构](hexagonal-architecture.md) |
| 改动常横穿整条用例 | [垂直切片](vertical-slice.md) |
| 领域有丰富易变业务规则 | [DDD](ddd.md) 战术构件 |
| 模型互相污染 / 跨库耦合 | [限界上下文](bounded-context.md) |
| 对外暴露 HTTP 能力 | [API 设计](api-design.md) |
| 读写负载不对称 | [CQRS](cqrs.md)（先轻量） |
| 需审计轨迹 / 时间旅行 | [事件溯源](event-sourcing.md) |
| 跨服务最终一致、无 2PC | [事件驱动](event-driven.md) + [Saga](saga.md) |
| 多客户端不同聚合视图 | [API 网关与 BFF](api-gateway-bff.md) |
| 多租户 | [多租户](multi-tenancy.md) |
| 统一审计 / 软删除 | [审计与软删除](auditing-soft-delete.md) |
| 怕边界随时间腐化 | [架构测试](architecture-tests.md) |

## 推荐组合

**默认栈（单进程、领域有逻辑、团队小）**
```
模块化单体
  └─ 整洁/六边形 内部组织
       └─ DDD 战术构件（实体 / 值对象 / 领域事件 / 服务 / DTO / 规约）
  └─ 解决方案分层（物理边界）
  └─ 架构测试（CI 锁边界）
  └─ ADR（决策留痕）
  └─ 按需：CQRS 轻量版、审计软删除、多租户
```

**进阶跨进程栈（部署/团队强制拆分时）**
```
模块化单体的"模块"即未来服务边界（= 限界上下文）
  └─ 拆微服务：每服务内部仍用同一套（整洁/六边形 + DDD 战术）
  └─ 跨服务：事件驱动（集成事件 + 发件箱）+ Saga（补偿）
  └─ 边缘：API 网关与 BFF（按客户端聚合）
  └─ 对外：API 设计契约
  └─ 贯穿：ADR + 架构测试
```
> 关键：微服务不是"更高级"，而是"更贵的部署形态"。能停在模块化单体就停——这是多数项目的正确终点。

## 学习 / 采用路径（由浅入深）

1. [模块化单体](modular-monolith.md) — 强边界单进程的地基。
2. [解决方案分层与项目引用](solution-structure.md) — 边界落到物理项目。
3. [整洁架构](clean-architecture.md) / [六边形架构](hexagonal-architecture.md) — 依赖方向与端口隔离。
4. DDD 战术构件：[实体与聚合根](entities.md) → [值对象](value-objects.md) → [领域事件](domain-events.md) → [领域/应用服务](domain-application-services.md) → [DTO](dto.md) → [规约模式](specification-pattern.md)（总览 [DDD](ddd.md)）。
5. [垂直切片](vertical-slice.md) — 换一个组织视角，与分层互补。
6. [架构测试](architecture-tests.md) — 把边界锁进 CI。
7. [CQRS](cqrs.md) — 何时才叠加读写分离。
8. [事件驱动](event-driven.md) + 发件箱 — 进程内副作用升级到跨进程。
9. [限界上下文](bounded-context.md) + [API 设计](api-design.md) — 跨边界模型隔离与契约。
10. [事件溯源](event-sourcing.md) — 已掌握 CQRS 之后才考虑。
11. [Saga](saga.md) — 跨服务最终一致，仅当真在多进程世界。
12. 横切按需：[多租户](multi-tenancy.md) · [审计与软删除](auditing-soft-delete.md)。
13. [API 网关与 BFF](api-gateway-bff.md) — 边缘聚合。
14. [ADR](adr.md) — 贯穿全程的治理，不是最后才做。
15. [微服务](microservices.md) — 确有强制理由才走，模块划分沿用第 1 步。

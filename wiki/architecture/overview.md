# 架构总览与决策指南

本页是架构区的**总入口**。其余架构页各自深入一个模式，但单独读像读小说——彼此孤立、看不出"什么场景该用什么、模式之间怎么拼"。这一页把它们的**关系、取舍与采用顺序**讲清楚，让你先建立体系，再按需下钻。

> 一句话心智：架构不是选一个"最佳模式"，而是**分层做一组相互咬合的决策**。下面三层由外到内，最外层定"怎么部署与切边界"，最内层定"代码怎么组织"，中间一层管"跨边界的模型与契约"，最后还有一组可随时叠加的横切能力。

---

## 一、心智模型：架构决策分三层（由外到内）

```
┌─────────────────────────────────────────────────────────────┐
│ 层 1 · 部署与边界形态（系统形态）                              │
│   单体还是微服务？模块边界画在哪？  → 模块化单体 / 微服务      │
├─────────────────────────────────────────────────────────────┤
│ 层 2 · 模块内部结构（代码怎么组织）                            │
│   依赖朝哪？按技术分层还是按功能？  → 整洁 / 六边形 / 垂直切片  │
│   + 战术 DDD 构件（实体/值对象/领域事件/服务/DTO/规约）        │
├─────────────────────────────────────────────────────────────┤
│ 层 3 · 战略设计与边界（跨模块/跨服务的契约）                   │
│   模型怎么隔离？对外契约怎么定？  → 限界上下文 / DDD 战略 /    │
│   API 设计 / ADR                                                │
├─────────────────────────────────────────────────────────────┤
│ 横切能力（任何形态上按需叠加）                                 │
│   CQRS / 事件溯源 / 事件驱动 / Saga / 多租户 / 审计软删除 /     │
│   架构测试 / 企业级模式导览                                     │
└─────────────────────────────────────────────────────────────┘
```

- **外层决定内层**：先想清楚"单进程还是多进程、模块边界在哪"，再决定模块内部怎么分层。反过来不成立——不要在还没定边界时就纠结 Clean vs Hexagonal 的细微差别。
- **横切能力是"叠加项"**：CQRS、事件溯源、Saga 等不是替代前面的选择，而是在某个具体痛点出现时才叠上去的开关。
- **物理边界先于人脑边界**：`解决方案分层与项目引用` 用编译期依赖把边界钉死，比任何文档都管用；`架构测试` 再把这条规则锁住，防止腐化。

## 二、模式地图（所有架构页归类）

| 层级 | 模式 | 一句话定位 | 深入页 |
|------|------|-----------|--------|
| 系统形态 | 模块化单体 | 单进程、内部强边界，运维简单又能清晰解耦 | [模块化单体](modular-monolith.md) |
| 系统形态 | 微服务 | 与模块化单体是"同一模块代码的二态"——只在部署/团队强制时才拆 | [微服务](microservices.md) |
| 系统形态 | 整洁架构 | 依赖只向内指向领域核心，分层清晰、易测 | [整洁架构](clean-architecture.md) |
| 系统形态 | 六边形架构 | 端口+适配器把 I/O 与外界隔离，业务不依赖基础设施 | [六边形架构](hexagonal-architecture.md) |
| 系统形态 | 垂直切片 | 按功能而非技术分层，改动局限在切片内 | [垂直切片](vertical-slice.md) |
| 系统形态 | 解决方案分层 | 物理项目边界与引用方向规则 | [解决方案分层](solution-structure.md) |
| 系统形态 | API 网关与 BFF | 边缘路由/聚合/横切；BFF 给每种客户端专属视图 | [API 网关与 BFF](api-gateway-bff.md) |
| 战略 | 限界上下文 | 战略 DDD 的边界单元，用通用语言与防腐层连接 | [限界上下文](bounded-context.md) |
| 战略 | DDD | 战术建模（聚合/实体/值对象/服务）+ 战略边界 | [领域驱动设计](ddd.md) |
| 战略 | API 设计 | 对外契约：资源/版本/状态码/分页/幂等/并发 | [API 设计模式](api-design.md) |
| 战略 | ADR | 每个重大架构决策留痕 | [架构决策记录](adr.md) |
| 模块内部 | 实体与聚合根 | 一致性/事务边界，按标识相等 | [实体与聚合根](entities.md) |
| 模块内部 | 值对象 | 无标识、按值相等、不可变描述 | [值对象](value-objects.md) |
| 模块内部 | 领域/应用服务 | 领域逻辑在领域，应用服务只编排用例 | [领域服务与应用服务](domain-application-services.md) |
| 模块内部 | DTO | 隔离领域与表现层，输入/输出分离 | [数据传输对象](dto.md) |
| 模块内部 | 领域事件 | 聚合收集、随工作单元分发（进程内同事务） | [领域事件](domain-events.md) |
| 模块内部 | 规约模式 | 把查询条件封装成可组合对象，返表达式树给 EF | [规约模式](specification-pattern.md) |
| 横切 | CQRS | 读写拆分；轻量同库即可，重量分库仅极端才用 | [CQRS](cqrs.md) |
| 横切 | 事件溯源 | 只追加事件流为事实来源，重放重建状态 | [事件溯源](event-sourcing.md) |
| 横切 | 事件驱动 | 用事件解耦生产者/消费者；区分领域事件与集成事件 | [事件驱动](event-driven.md) |
| 横切 | Saga | 跨服务补偿式最终一致，无 2PC | [Saga](saga.md) |
| 横切 | 多租户 | 全局查询筛选器自动隔离租户数据 | [多租户](multi-tenancy.md) |
| 横切 | 审计与软删除 | SaveChanges 拦截器统一填充，筛选器自动隐藏 | [审计与软删除](auditing-soft-delete.md) |
| 横切 | 架构测试 | 用反射/Roslyn 强制分层与依赖方向 | [架构测试](architecture-tests.md) |
| 横切 | 企业级模式导览 | 上述模式的企业级落地速查 | [企业级架构模式](enterprise-patterns.md) |

另有 [组合与架构模式](../patterns/composition.md) 与 [设计与可维护性反模式](../anti-patterns/design-antipatterns.md) 作配套参考。

## 三、何时用何种：决策指南

按"你正面对的情况"对号入座。**优先从最上面的默认项开始，只有痛点出现才往下叠加。**

**A. 先定部署与边界形态**
- 一个团队、部署简单、领域还在演化 → 默认 **[模块化单体](modular-monolith.md)**。内部用强边界模拟微服务，将来要拆时边界已是现成的。
- 需要多个团队独立部署、或不同部分伸缩曲线差异巨大 → 才上 **[微服务](microservices.md)**。注意：微服务是模块化单体的"二态"，模块划分方式一致，只是部署单元变了。

**B. 再定模块内部结构**
- 想要"依赖只向内、易替换存储、易测" → **[整洁架构](clean-architecture.md)** 或 **[六边形架构](hexagonal-architecture.md)**（二者目标一致，六边形更强调端口隔离 I/O）。
- 功能多、改动的"横切面"常是整条用例而非某一层 → 考虑 **[垂直切片](vertical-slice.md)**，与分层互补而非互斥。
- 用 **[解决方案分层](solution-structure.md)** 把上述边界落到物理项目引用上。

**C. 叠加战术 DDD 构件（当领域有真实逻辑时）**
- 有身份与生命周期的概念 → **[实体与聚合根](entities.md)**；无标识的描述性概念 → **[值对象](value-objects.md)**。
- 跨聚合的业务 → **[领域/应用服务](domain-application-services.md)**；进程内副作用 → **[领域事件](domain-events.md)**。
- 表现层隔离 → **[DTO](dto.md)**；可复用查询条件 → **[规约模式](specification-pattern.md)**。

**D. 跨边界的模型与契约（当系统不止一个边界时）**
- 模型开始互相污染、跨库耦合 → 划 **[限界上下文](bounded-context.md)**，用防腐层翻译。
- 对外暴露能力 → 定 **[API 设计](api-design.md)** 契约。
- 任何重大取舍 → 写 **[ADR](adr.md)** 留痕。

**E. 按需叠加横切能力（出现具体痛点才开）**
- 读写负载不对称、读路径要独立优化 → **[CQRS](cqrs.md)**（先轻量同库）。
- 需要完整审计轨迹 / 时间旅行 / 强一致事件流 → **[事件溯源](event-sourcing.md)**（常与 CQRS 同用）。
- 跨服务最终一致、不能有 2PC → **[Saga](saga.md)** + **[事件驱动](event-driven.md)**（集成事件 + 发件箱）。
- 多客户需不同聚合视图、怕上帝网关 → **[API 网关与 BFF](api-gateway-bff.md)**。
- 多租户数据隔离 → **[多租户](multi-tenancy.md)**；统一审计/软删除 → **[审计与软删除](auditing-soft-delete.md)**。
- 怕边界随时间腐化 → **[架构测试](architecture-tests.md)** 把规则锁进 CI。

## 四、模式如何组合：推荐技术栈

**默认栈（单进程、领域有逻辑、团队小）**

```
模块化单体
  └─ 整洁/六边形 内部组织
       └─ 战术 DDD（实体 / 值对象 / 领域事件 / 服务 / DTO / 规约）
  └─ 解决方案分层（物理边界）
  └─ 架构测试（CI 锁边界）
  └─ ADR（决策留痕）
  └─ 按需：CQRS 轻量版、审计软删除、多租户
```

**进阶跨进程栈（团队/部署强制拆分时）**

```
先把模块化单体的"模块"当作未来服务的边界（限界上下文）
  └─ 拆微服务：每个服务内部仍用同一套（整洁/六边形 + DDD 战术）
  └─ 跨服务：事件驱动（集成事件 + 发件箱）+ Saga（补偿）
  └─ 边缘：API 网关与 BFF（按客户端聚合）
  └─ 对外：API 设计契约
  └─ 贯穿：ADR + 架构测试
```

> 关键认知：**微服务不是"更高级"，而是"更贵的部署形态"**。它用运维复杂度换独立部署与独立伸缩。能停留在模块化单体就停留——这是多数项目的正确终点。

## 五、由浅入深的学习 / 采用路径

按下面顺序读与落地，每一步都建立在前一步之上，避免一上来就被模式名词淹没：

1. **[模块化单体](modular-monolith.md)** —— 先建立"强边界单进程"的心智，这是后面一切的地基。
2. **[解决方案分层与项目引用](solution-structure.md)** —— 把边界落到物理项目与引用方向上。
3. **[整洁架构](clean-architecture.md)** 与 **[六边形架构](hexagonal-architecture.md)** —— 理解依赖方向与端口隔离（二选一或混用）。
4. **战术 DDD 构件**：[实体与聚合根](entities.md) → [值对象](value-objects.md) → [领域事件](domain-events.md) → [领域服务与应用服务](domain-application-services.md) → [DTO](dto.md) → [规约模式](specification-pattern.md)。
5. **[垂直切片](vertical-slice.md)** —— 换一个组织视角，与分层互补。
6. **[架构测试](architecture-tests.md)** —— 把上面的边界锁进 CI，防止腐化。
7. **[CQRS](cqrs.md)** —— 学会"何时才叠加读写分离"（多数时候不需要）。
8. **[事件驱动](event-driven.md)** + [领域事件](domain-events.md) + 发件箱 —— 进程内副作用升级到跨进程。
9. **[限界上下文](bounded-context.md)** + [DDD 战略](ddd.md) + [API 设计](api-design.md)** —— 处理跨边界的模型隔离与对外契约。
10. **[事件溯源](event-sourcing.md)** —— 在已掌握 CQRS 之后，才考虑用事件流当事实来源。
11. **[Saga](saga.md)** —— 跨服务最终一致，仅当你真的在多进程世界。
12. 横切能力按需取用：[多租户](multi-tenancy.md)、[审计与软删除](auditing-soft-delete.md)。
13. **[API 网关与 BFF](api-gateway-bff.md)** —— 边缘聚合与横切。
14. **[ADR](adr.md)** —— 贯穿全程的治理，不是最后才做。
15. **[微服务](microservices.md)** —— 放在最后：当你确有部署/团队强制理由时才走这一步，且模块划分沿用第 1 步。

配套速查：[企业级架构模式（导览）](enterprise-patterns.md)、[组合与架构模式](../patterns/composition.md)、[设计与可维护性反模式](../anti-patterns/design-antipatterns.md)。

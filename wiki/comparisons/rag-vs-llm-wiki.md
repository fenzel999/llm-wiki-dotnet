> **要点速览**
> - RAG 在查询时检索外部资料；LLM Wiki 在摄入时编译为结构化知识。
> - 本仓库选 LLM Wiki：知识随贡献累积、互链、可视化、可自校正。
> - 二者可互补，但本库以"摄入即编译"为核心范式。

## 概述

当你想让一个大模型"懂点它训练时没见过的东西"，基本只有两条路。一条叫 **RAG**（检索增强生成，Retrieval-Augmented Generation），思路是：模型自己记不住的，就在用户提问的那一刻去外面检索——把语料切成片段、向量化，提问时召回到最相关的几段，拼进提示词再让模型作答。另一条路更"慢工出细活"，叫 **LLM Wiki（摄入时编译知识库）**：你（或者你的 Agent）在资料进来的时候就把它们消化、提炼、整理成一篇篇带出处引用的结构化 Markdown，等真正要用时，知识早就在那儿了，直接顺着链接读就行。

这两种范式不是"谁更先进"的关系，而是解决不同问题的两种口味。RAG 把复杂度留到查询时刻——它适合"资料多到理不完、而且天天在变"的场景；LLM Wiki 把复杂度前置到摄入时刻，适合"知识相对稳定、但你容不得模型胡说、还要能查得到每一句话是谁说的"的工程库。说白了：**RAG 是让模型在提问时临时翻书，LLM Wiki 是你先把书读薄、写成笔记，以后随时翻。** 本仓库（这个 .NET / C# 知识库）走的就是后一条路。

## 取舍对比

| 维度 | RAG（检索增强生成） | LLM Wiki（摄入时编译知识库） |
|------|---------------------|------------------------------|
| 检索时机 | 查询时实时检索(retrieval at query time) | 摄入时预先编译(compile at ingest time)为结构化页面 |
| 延迟 | 每次查询需向量召回+重排，额外延迟 | 知识已在页内，定位快、可直接链接 |
| 一致性 | 依赖检索质量，可能召回过时/无关片段 | 知识经人工/审核沉淀，版本化、可审计 |
| 可维护性 | 语料与索引分离，需维护向量库 | 纯 Markdown，Git 版本控制、差异可读 |
| 可解释性 | 检索结果黑盒、难追溯 | 每页有 `source` 来源 cite，链路透明 |
| 成本 | 运行时检索+嵌入推理持续开销 | 摄入期一次性整理，运行期零检索成本 |
| 适用 | 海量/常变动态语料、开放问答 | 稳定领域知识、需要确定性与可维护性的工程库 |

什么时候该选 RAG？典型信号是：你的语料规模大到根本不可能人工整理，而且它还在持续变化——今天改一版文档、明天又发布个新版本。这种场景下你没法"预先编译"，只能依赖运行时去把最相关的内容捞出来。RAG 还擅长那种长尾、没法预测用户会问什么的问题，因为它每次都现去检索最贴近当下的片段。

什么时候该选 LLM Wiki？当你的知识域本身比较稳定（比如一门语言的标准写法、某框架的最佳实践），你最关心的不是"能否覆盖一切未知问题"，而是"说出来的东西准不准、能不能追责、下次还想改的时候好不好改"。把知识在摄入时整理成结构化页面，意味着它进版本库（Git）、有差异可看、有 `source` 指向原始出处，而且运行期没有任何检索开销——页面本身就是答案，不需要先去向量库里碰运气。这也顺带满足了 [POLICY](../governance/policy.md) 里那条"一律用相对路径链接"的约定，让整个知识库能互相串成一张网。

两种路线写出来的代码长得很不一样，一眼就能区分：

```csharp
// RAG：查询时检索（示意）
var hits = await vectorStore.Search(embeddingOf(query), topK: 5);
var context = string.Join("\n", hits.Select(h => h.Text));
var answer = await llm.Complete($"上下文:\n{context}\n\n问题:{query}");

// LLM Wiki：摄入时编译为结构化页，运行期直接定位
// 页面本身即知识，Agent 通过相对链接读取：
//   [record 值语义](../dotnet/csharp/modern-csharp.md#records)
//   [RAG vs LLM Wiki](comparisons/rag-vs-llm-wiki.md)
// 无运行期检索成本，一致性由 POLICY 审核保证。
```

RAG 那段代码每次被调用都要付"向量召回 + 重排 + 嵌入推理"的账；而 LLM Wiki 这边，知识已经在页面里躺好了，运行期就是一个普通的文件读取加链接跳转，成本接近于零。

## 结论与建议

如果用一个判断标准来收尾，那就是：**你的知识会不会一直变、变到理不过来？**

如果你的领域知识相对稳定、你又特别在乎"确定性、可维护、可审计"——这正是绝大多数工程库的真实处境——那 LLM Wiki 几乎是理所当然的选择。把那些惯用法、反模式、团队约定在摄入时就编译成带 `source` 引用的 Markdown，你既躲开了 RAG 那种"检索偶尔抽风、召回了过时的片段"的风险，又让工具链和 Agent 能直接用相对链接引用知识点，而不是每次都去赌向量库召回得对不对。

只有当你面对的是"海量、且持续变化、长尾问题根本无法预先归纳"的语料时，RAG 的向量库与运行时开销才值得你去背。对于本仓库这种"把 .NET / C# 的正确用法沉淀下来"的目标，显然前者更合适——这也是我们采用 LLM Wiki 策略的原因。

# POLICY — 持久约定（最高优先级）

本文件记录**长期有效、跨页面必须遵守**的规则。Agent 每次会话先读它；Audit/Correct 时若与
某页冲突，以本文件为准。反复出现的同类错误应被提炼成新规则（自学习）。

---

## P1 优先使用最新惯用法
当某特性有更新、更推荐的写法（如 `field` 关键字替代老式属性样板、`extension` 块替代
静态扩展类），页面必须展示**最新做法为首选**，并把旧写法标为「历史/不推荐」而非并列等价。

## P2 反模式页必须含好/坏对比
`anti-patterns/` 下每页须同时给出「❌ 错误写法」与「✅ 正确写法」，且解释**为什么**坏。

## P3 每页必 cite 来源
正文或 frontmatter `source` 必须指向 `wiki/sources/` 内条目或外部官方 URL。无来源不写事实。

## P4 版本差异用选项卡
同一主题在不同 .NET 版本行为不同时，用 `=== "net10"` / `=== "net11"` 选项卡对比，
不在正文里用自然语言含糊说「新版改了」。

## P5 禁止静默覆盖矛盾
发现与既有页矛盾时，标 `⚠️` 并写入 `qa-report.md`，先问人类，不要直接覆盖。

## P6 代码示例可编译优先
给出的 C# 片段尽量为可编译的最小片段；确实需要省略时用 `// ...` 注明，不写语法错误代码。

## P7 中文为主、术语保留英文
页面用中文叙述，技术术语（如 `record`、`Span`、`AOT`）保留英文原词并在首次出现时给中文注解。

## P8 链接用相对路径
内部链接一律相对 Markdown 链接，确保 GitHub / MkDocs / 网页三处都可解析。

## P9 索引与可视化随内容同步
`index.md`、`思维导图.md` 在每次 Ingest/Correct 后必须更新，禁止过期。

## P10 只用微软官方或 .NET 基金会的包，其余手写
知识库示例与推荐**只允许**依赖：①微软官方包（`Microsoft.*`、`System.*`、`dotnet` 内置）；
②.NET 基金会（.NET Foundation）成员项目（如 xUnit、Polly、NUnit）。
**任何其他第三方包一律不推荐、不示范**——遇到其功能，改为用内置 API **手写实现**（如手写测试替身
代替 Moq、手写断言辅助代替 FluentAssertions、手写 HTTP 封装代替 Flurl）。
如某功能确无 MS/基金会方案且无法合理手写，标 `⚠️ needs-your-call` 并写入 `qa-report.md`，先问人类。

## P11 删旧换新（Audit/Correct 主线）
整理知识时以"新知识替代旧知识"为默认动作：过时/被取代的写法**删除**，仅当新方案无法覆盖旧场景时
才保留旧知识，并显式标注"仅用于 X 场景，通用场景已被 Y 取代"。这是 P1 在全库整理时的强化。

## P13 页面结构对 AI 与人类双友好
每个内容页在 frontmatter 之后、`## 概述` 之前，加一个 **`> **要点速览**`** 引用块（3–6 条 bullet），
用最短的话给出本页结论/关键规则。目的：人类可秒扫、AI 可零解析提取事实。
配套：正文保持固定小节（`概述` / `正确做法` / `常见误区` / `适用版本` / `参考资料`），
好坏代码统一用 `✅` / `❌` 标注并写明"为什么"。

## P12 不用需付费/云绑定的组件
示例与推荐**不依赖**需要付费或绑定特定云的组件（如 Azure 各托管服务、Application Insights、
Orleans 等）。技术讲解保持**厂商中立**：可观测性导出用 OTLP + 开源后端（Prometheus/Grafana/Jaeger）、
消息/事件用通用概念或可自托管的开源实现、部署讲通用容器。免费且开源的微软官方项目（如 .NET Aspire
本体、Docker 化）可用，但不引导用户走向必须付费的云服务。

## P14 只吸收架构思想，正文与来源不得出现特定框架名（ABP）
学习企业架构（模块化、DDD 分层、领域/应用服务、规约、多租户、审计/软删除、事件总线）时可**参阅 ABP
框架文档汲取思想**，但知识页**正文、标题、summary、`source`、参考资料一律不得出现 "ABP" 字样**，
也不得引用 `abp.io` 链接。全部以**微软官方文档**表述与引用（EF Core 全局查询筛选器 / 拦截器、
.NET 微服务 DDD/CQRS 架构指南等），实现用微软内置 + 手写 + Minimal API。

## P15 API 用真实 HTTP 状态码，不用统一 Result 包装
Web/API 边界一律返回**真实 HTTP 状态码**表达结果：成功 200/201/204，客户端错误 400（请求格式错）、
401/403（认证/授权）、404（资源不存在）、409（冲突）、**422（语义/业务校验失败）**，服务器错误 5xx。
**禁止**再包一层"永远 200 + `{ success, data, error }`"的统一返回类（`Result<T>` 信封）；
错误统一走 [`ProblemDetails`](../dotnet/aspnet-core/exception-handling.md)（RFC 9457）。
最小 API 用 `TypedResults`/`Results<T>` 表达多结果，不自造联合返回类型。
注意：这与**分页载体** `PagedResult<T>`（承载 items+total 的数据结构）无关，后者是合法数据模型。

## P16 后端代码必须 Native AOT 兼容（前端豁免）
服务端/后端（API、应用服务、领域、基础设施、后台服务）的推荐写法**必须兼容 Native AOT**：
- 只用 [Minimal API](../dotnet/aspnet-core/aspnet-core-10.md)，**不用 MVC/控制器**（不支持 AOT）；
- **禁止运行期反射 / 动态代码生成**；JSON 用 System.Text.Json **源生成**（[`JsonSerializerContext`](../dotnet/csharp/source-generators.md)），不用反射序列化；
- EF Core 在 AOT 发布下用**编译模型 / 预编译查询**；查询逻辑本身不得靠反射构建（如[动态排序用编译期表达式白名单](../dotnet/ef-core/pagination.md)，不按字符串反射属性名）；
- DI 用**显式注册**，避免运行期程序集扫描。

**前端（Blazor 等 UI 层）豁免**本规则（Blazor Server 不支持 AOT、WASM 另有 AOT 路径），但相关页仍须在「AOT 兼容性」小节说明限制。
后端确需暂不支持 AOT 的能力（如 cookie/OIDC 认证）时，须在页面标「AOT 兼容性」并给出 AOT 友好替代（如 JWT）；无法替代则 `⚠️ needs-your-call` 并写入 `qa-report.md`。

每个后端主题页在「适用版本」后应含一个 **`### Native AOT 兼容性`** 小节，说明是否兼容、限制与替代。

## P17 页面须"可教会"，自足且深度完整（面向知识过时的 LLM）
本库是 **LLM Wiki**：读者可能是知识停留在较早年份的模型。页面不能只写"结论式提醒"，必须**自足到能教会一个不懂此主题的模型去解决真实问题**。因此**基础/后端主题页**须满足：
- **能力全景**：覆盖该主题的**完整能力面**（不是只给 happy path）。例：讲依赖注入不能只讲三生命周期，还要覆盖键控服务、`IEnumerable` 多注册、`TryAdd*`、工厂/开放泛型注册、作用域工厂、释放语义、启动期校验等。
- **多个可运行示例**：不同变体各给最小示例，不是一个例子讲到底。
- **决策指引**：给"何时用哪个"的判断（表格/清单），而非只罗列 API。
- **边界与坑**：常见误区给足（≥3 条）并解释**为什么**。
- **版本增量**：标清各能力**引入版本**（如键控服务 net8+），让旧模型知道哪些是新的。
- 仍保留 `> **要点速览**` 供人类秒扫；深度放在 `## 正确做法` 的分节里。

判断标准：**"一个 2024 年知识的模型只读这一页，能不能正确解决该主题下的常见任务？"** 不能，就是没写够。宁可长而完整，不要短而残缺。
